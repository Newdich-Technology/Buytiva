# Procurement implementation status

The repository contains functioning identity routes and repositories, but most procurement files are empty. `order.prisma` and `payment.prisma` contain no models; `quotation.prisma` currently contains shopping requests, not quotations. Shopping-list routes are registered when their repository is provided. Checkout, ledger, and payout implementations are absent. The pricing preview is nonbinding and is not checkout; production use requires business-rule approval.

## Work added

Shopping lists now have Prisma models and authenticated customer routes for creating, reading, paging, adding, replacing and removing items, deleting drafts, and submitting nonempty drafts. Prices are stored as integer minor units and quantity as thousandths. Submitting only freezes the list; it does not select an address, create a quote or order, or initiate payment. Draft mutations serialize through a parent-row update within a transaction. Production rollout still requires a reviewed migration; CI uses a disposable synchronized schema.

`calculatePricingQuery` is an isolated deterministic calculation using integer minor units and thousandths for quantities. It rounds each line and each fee half-up. Its **proposed**, not yet approved, rule charges the fixed fee at or below the threshold and a percentage of the entire subtotal above it; commission is deducted from the service fee. It copies and freezes an in-memory result, but this is not a durable immutable snapshot. It is now used for a nonbinding price preview based on persisted list, address, delivery zone and versioned procurer policy; no quotation or payment flow is wired to it. The operator must confirm the threshold, rounding, quantity precision, currency and commission rules before production use.

The OTP and MFA retry counters now atomically increment every concurrent invalid attempt rather than using a stale attempt count as a compare-and-set. Challenge consumption still uses compare-and-set. The new PostgreSQL concurrency tests require a dedicated disposable `AUTH_TEST_DATABASE_URL`; they run in the disposable PostgreSQL service in CI; PostgreSQL is unavailable in this workspace.

## Operational profile and service zones

`GET/PUT /api/v1/procurer-services/me` and `POST/PUT /api/v1/procurer-services/me/zones[/{zoneId}]` require an active, MFA-authenticated procurer. Mutable fields are public name, biography, accepting-requests flag and owned zones. `GET /api/v1/procurers/discovery?country=NG&region=FCT&city=Abuja&area=Wuse` requires an active customer and returns only active, accepting profiles with approved, verified, compliant applications, an accepted invitation, active verified user and role, enabled MFA and an exact active zone. Country is a two-letter code; region/city/area are NFKC-normalized, whitespace-collapsed, case-folded strings, and all four must match exactly. This is not a standardized authoritative location registry; spelling variants are not resolved. Zones have NGN delivery fees as minor-unit strings. Discovery is paginated and ordered by public name and zone ID. It excludes confidential identity evidence. Invitation ownership is checked after page selection, so inconsistent legacy invitation data may produce short pages; cursor-based pagination and a database-enforced relationship are follow-up work. It provides the current service-fee policy but does not report rating summaries; reviews do not yet exist.

A procurer cannot update verification or approval through these APIs. Profiles default to not accepting requests. Zone uniqueness is enforced by database constraint. A customer must not rely on a discovery response as a permanent eligibility decision; no quotation/order process exists yet to revalidate it. Deployment requires reviewed migrations before enabling routes; the existing `db:sync` remains restricted to disposable databases.

## Versioned pricing and nonbinding preview

MFA-authenticated active procurers can `GET /api/v1/procurer-services/me/pricing` and `PUT` the same path with `currency`, `fixedFeeMinor`, `thresholdMinor`, `percentageBasisPoints` and `expectedVersion`. The first version uses expectedVersion 0. Every update appends a version and a concurrent stale update gets 409. Discovery excludes profiles with no configured policy and includes the current public policy. `POST /api/v1/pricing/preview` accepts only `addressId`, `listId`, and `procurerId`; it reads the customer's own saved address and list and rechecks the active procurer and exact zone. It computes subtotal, procurement fee, delivery fee and customer total in NGN minor-unit strings, marked `binding: false`. It is not an offer, an immutable quotation, or a payment request. Data are read separately, so concurrent edits can yield a mixed or immediately stale preview; a future quotation must re-read, lock/revalidate and snapshot its inputs transactionally.

The provisional rule remains fixed fee at or below threshold and percentage of the whole subtotal above it, with half-up rounding. Product must approve it before a paid launch. Platform commission is not configured here, is not reported as zero, and cannot be set by a procurer; it must be derived from an approved independently managed versioned policy at quotation/settlement. Commission must come from the service fee, not be silently added twice to customer totals.

## Customer addresses and list naming

Authenticated customers can create, list, retrieve, update and delete their own addresses at `/api/v1/addresses` and `/api/v1/addresses/{addressId}`. `GET /api/v1/addresses/{addressId}/procurers` derives the discovery location from a customer-owned saved address. Missing and other customers' address IDs both return 404. Address lookups use normalized exact matching; address updates are not a quotation snapshot and must be revalidated and copied into a future order transaction. A location with no matches returns an empty array. Shopping requests copy a selected address; no order or quotation currently exists. Customers can rename their own draft list with `PATCH /api/v1/shopping-lists/{listId}`; submitted lists remain immutable.

## Submitted shopping requests

A customer can `POST /api/v1/shopping-requests` with their own submitted `listId`, `addressId`, and selected `procurerId`. The serializable transaction rechecks the submitted list, customer ownership, current procurer approval and compliance, accepted invitation, active account and MFA, availability, pricing policy and exact active delivery zone. It persists independent list and address snapshots and creates one request per list/procurer pair. A repeat or concurrent duplicate returns 409; cancellation does not free the pair for reuse. `GET /api/v1/shopping-requests`, `GET /api/v1/shopping-requests/{requestId}` and `POST /api/v1/shopping-requests/{requestId}/cancel` are customer-owned. The assigned procurer can use `GET /api/v1/procurer-services/me/requests` and `GET /api/v1/procurer-services/me/requests/{requestId}`. Other users receive 404. The snapshot is not a quotation, reserves no price, initiates no payment, sends no notification and does not create an order. Future quote issuance must recheck eligibility and current fee policy and transactionally serialize against cancellation.

## Database deployment constraint

Prisma 7.10 uses Prisma Client generated from the multi-file schema; existing `db:sync` uses `prisma db push`, not a versioned migration. There are no migration files. A blanket prohibition on checked-in SQL conflicts with Prisma Migrate's SQL migration history. Do not use `db push` against production as a workaround. Agree on a reviewed production migration mechanism with versioned, auditable changes, backups, rollback/recovery and a disposable rehearsal before adding deployed procurement models. The PostgreSQL integration suites delete records and must never target a production/shared database.

## Shopping-list HTTP example

With a verified, active CUSTOMER access token, create a draft using `POST /api/v1/shopping-lists` and `{ "title": "Weekly shop", "currency": "NGN" }`. A successful response is `201` with a list `id`, `status: "DRAFT"`, and an empty `items` array. Add an item with `POST /api/v1/shopping-lists/{id}/items` and `{ "name": "Rice", "quantity": "1.250", "expectedUnitPriceMinor": "250000" }`. Submit with `POST /api/v1/shopping-lists/{id}/submit`; a successful `200` returns the list with `status: "SUBMITTED"`. The API supports NGN only until an authoritative currency configuration is available. Request and response schemas appear in `/api/v1/docs`. Draft list and item lookups are scoped to the authenticated customer; a different customer receives `404`. Submissions are one-way and no quote or procurer is created.
