# Initial private verified-order review policy

Only the active, email-verified customer with the CUSTOMER role can submit one review for an order they own. The server derives customer and procurer from the order/request, never client input. The order must be `COMPLETED`, have a `COMPLETED` history entry by that customer, and retain a non-reversed, non-future verified payment with exactly the quotation amount and currency. Self-review is denied. Eligibility and unique insertion are inside a serializable transaction with a database unique constraint on `orderId`; concurrent attempts fail closed on uniqueness/serialization conflicts. This implements a narrow admission rule, not all Phase 2B requirements.

`POST /api/v1/orders/:orderId/review` accepts integer `rating` 1–5 and optional plain-text comment (max 2000 characters); `GET` at that path reads only the owner's review. Global and route-specific rate limits apply. Review text is untrusted, and JSON responses must never be rendered as HTML. There is no public review listing, aggregate, report or procurer response. Permissioned administrators can auditably approve, hide or reinstate private reviews; these statuses do not yet expose reviews publicly. Reviews remain private until abuse controls, refund handling and public presentation policies are implemented and tested. There is no fabricated rating and no public payment writer.

A reversed payment blocks new reviews; an existing review remains available privately to its owner. No refund model/provider integration exists, so real-world refund/dispute and post-completion reversal handling remain release blockers. Review records do not prove real provider payment: isolated tests insert a test payment record. Production deployment requires a reviewed migration, product approval of review eligibility/edit/moderation rules, and a future payment integration that coordinates reversal/refund visibility before any public exposure.

Moderation is restricted to active staff with the explicit `reviews.moderate` permission (or Super Admin), with recent MFA for decisions. Neither the review author nor assigned procurer may moderate their own order even with staff permissions. Every change requires an expected previous state and review version, a reason, and a transactional audit record. Negative sentiment alone is not a legitimate moderation reason. PostgreSQL regression passed CI 45670541457.

An internal, permission-protected rating summary computes averages and distributions from approved reviews with valid completion and matching non-reversed payment, using a consistent read snapshot. CI 45671161336 exercises moderation and reversal transitions. It is not exposed publicly; refund policy, multi-rating rounding coverage and scalability remain open.

Owners may replace an eligible review with `PUT /api/v1/orders/:orderId/review`, supplying its expected version. The server rechecks completion and payment, rejects hidden reviews and stale versions, increments the version and resets moderation to pending. A moderator must specify the version inspected, preventing approval of unseen edits. PostgreSQL CI for editing is pending; policy requires product approval before public use.
